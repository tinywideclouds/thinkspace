# Workspace Architecture

The `workspace` package is the domain core of ThinkSpace. It manages the physical state of agent conversations, Git-backed version control, virtual sandboxes, and multi-tenant environment routing. It uses a CQRS/Event Sourcing dual-write architecture via `thinkgraph.Dispatcher`, separating the immutable append-only JSONL ledger on disk from the fast BadgerDB read graph.

## Core Concepts

*   **Thread:** Represents the accepted conversation branch, mapped to `refs/heads/chat/{id}`.
*   **Candidate:** Represents a speculative branch holding unverified tool outputs and file modifications generated by a sub-agent, mapped to `refs/heads/candidate/{id}`.
*   **Candidate Sandbox:** A physically isolated, short-lived working directory where agents can safely create, read, and modify files before delivery and review.

## The Dual-Write Architecture

### 1. The Write Model (`thinkgraph.FileLedger`)
`thinkgraph.Dispatcher` appends events, digests, mutations, and space contexts directly to sharded JSONL files under `chats/{id}/ledger/` (`logs/`, `digests/`, `mutations/`, `contexts/`) so the cognitive history is version-controlled and survives database resets.

### 2. The Read Model (`thinkgraph.GraphRepository` / BadgerDB)
`thinkgraph.GraphStore` mirrors all ledger writes into a multi-tenant `BadgerDB` instance (typically at `.graphdb`) using `{ProjectID}:{ChatID}` routing keys for fast timeline extraction, sticky digests, and semantic `#tags`.

### 3. Glass Box Rehydration (`Service.SyncGraphContext`)
Before serving a timeline or subgraph, `Service.SyncGraphContext` walks branch ancestry via `EventBranchAnchor` headers (or isolates `flow-*` subgraphs directly) and invokes `thinkgraph.Rehydrator` to fast-forward (`SyncStatusBehind`) or rebuild (`SyncStatusMismatch`) the BadgerDB index from disk.

## Core Components

### 1. `ServiceManager` (`manager.go`)
Handles stateless, multi-tenant operations requested by the REST API, caching lazily instantiated `Service` instances locked to a `SpaceID`, managing atomic JSON persistence (`space.json`, `settings.json`, `meta.json`), and holding the shared `GraphRepository` connection.

### 2. `Service` (`service.go`)
Orchestrates the active lifecycle of a single ThinkSpace: chat initialization, JIT graph synchronization, candidate sandbox spawning, candidate acceptance/rejection, context previews, and ledger/digest persistence through `thinkgraph.Dispatcher`.

### 3. `ChatVersioner` & Sandbox Capability Interfaces (`state.go`)
`ChatVersioner` abstracts raw VCS manipulation (thread initialization, checkpoints, candidate worktree sandboxes, diff inspection, accept fast-forwards, and reject cleanup). Sandbox capabilities are decomposed into narrow interfaces (`FileReader`, `FileWorkspace`, `CommandRunner`) composed into `CandidateSandbox`.

### 4. `Patcher` & `Workbench` (`patcher.go`, `workbench.go`)
`Patcher` applies structured LLM patch outputs to a `FileWorkspace`; `Workbench` reads requested target files from a `FileReader` into `cognition.WorkbenchItem` entries with fail-fast validation on missing paths.
