# Workspace Architecture

The `workspace` package is the domain core of ThinkSpace. It manages the physical state of agent conversations, Git-backed version control, virtual sandboxes, and multi-tenant environment routing. It is heavily influenced by the Event Sourcing pattern, separating the immutable log (Write Model) from the contextual projections (Read Model).

## Core Concepts

*   **Thread:** Represents the "Slow" branch of a conversation. It is the accepted ledger of reality, mapped to `refs/heads/chat/{id}`.
*   **Candidate:** Represents a "Fast" branch. It holds unverified tool outputs and file modifications generated by a sub-agent, mapped to `refs/heads/candidate/{id}`.
*   **Candidate Sandbox:** A physically isolated, short-lived working directory (usually a Git worktree or clone) where agents can safely create, read, and modify files before they are merged into the main Thread.
*   **Flow Receipts:** XML-based artifacts (`receipts/{flow_id}.xml`) that permanently record the execution trace, agent fan-outs, and verification results of complex workflows.

## The Ledger (Write Model)
The `conversation.jsonl` file serves as the raw, append-only Write Model. It logs `Event` objects representing everything that has happened: user prompts, model responses, tool invocations, candidate proposals, and resolutions. The Ledger is unaware of how this data will be used; its only job is to immutably record facts.

## Projections (Read Model)
Because injecting the entire Ledger into an LLM context window is cost-prohibitive, the system projects the raw events into specific navigational maps (`chat.PlaybackEngine`):
*   **`ThreadManifest`:** The Read Model projection defining the available semantic lenses and summaries.
*   **`DigestMeta`:** Highly compressed summaries of older events. "Sticky" digests are always injected into the context window to preserve critical rules or overarching architecture.
*   **`Lenses`:** A routing index mapping a semantic conceptual tag (e.g., `#authentication`) to a list of literal `Event UUIDs`. This allows the LLM to query a tag and immediately retrieve the historical subgraph without performing an expensive, full-text scan of the ledger.

## Core Components

### 1. ServiceManager (The Registry & Librarian)
The `ServiceManager` sits at the top of the domain hierarchy. It handles all stateless, multi-tenant operations requested by the REST API:
*   **Directory CRUD:** Scanning and creating chat directories (`meta.json` management, UUIDv7 generation, auto-incrementing naming).
*   **Service Routing & Caching:** Lazily instantiating and holding active `Service` instances locked to a specific `spaceID`.

### 2. Service (The Session Orchestrator)
The `Service` is dedicated entirely to the active lifecycle of a single ThinkSpace. It is isolated and unaware of other spaces.
*   **Ledger Management:** Appends serialized interaction events to the `conversation.jsonl` ledger.
*   **Subgraph Extraction:** Provides agnostic retrieval (`FetchEvents`) to blindly extract UUIDs mapped by the projections.
*   **Agent Orchestration:** Manages virtual sandboxes, physical file I/O, and fast-forwarding or dropping candidate branches upon human resolution.
*   **Receipt Storage:** Marshals and persists `FlowReceipt` structures to disk.

### 3. ChatEngine (The Git Backend)
An interface that handles raw version control manipulation. It operates solely on the directory it was initialized with.
*   `GoGitEngine`: A pure Go implementation using `go-git` for in-memory, portable repository operations.
*   `GoExecEngine`: A wrapper around the native `git` CLI, utilizing native `git worktree` for performant candidate sandboxing.

## Architectural Strategy: The Multi-Service Registry

To support fluid context switching across multiple workspaces, ThinkSpace uses a Multi-Service Registry pattern at the top level, rather than pushing routing logic down into the file system layer. 

When a user requests a space, the `ServiceManager` boots a dedicated `Service` and `ChatEngine` locked strictly to that specific directory and caches it in memory. This strategy explicitly supports power-user workflows:

1.  **Instant Context Switching:** Because the `ServiceManager` caches the services in memory, the Git engines remain "warm". Switching back and forth between different workspaces feels instant, as it prevents the system from having to repeatedly re-parse `.git` directories from disk on every switch.
2.  **State Isolation:** Power users often run long, heavy agent tasks. Because each space runs on its own dedicated `Service` instance, mutex locks, agent fan-outs, and file I/O in one workspace will never block or collide with operations running in another.
3.  **Pure Encapsulation:** The highly complex, fragile logic inside the `gitfs` layer (such as floating ledger checkouts) remains completely decoupled from domain routing concerns. It only ever has to think about a single repository.
