# Workspace Architecture

The `workspace` package is the domain core of ThinkSpace. It manages the physical state of agent conversations, Git-backed version control, virtual sandboxes, and multi-tenant environment routing. It utilizes a strict CQRS/Event Sourcing dual-write architecture, completely separating the immutable Git audit trail from the fast BadgerDB read graph.

## Core Concepts

*   **Thread:** Represents the "Slow" branch of a conversation. It is the accepted ledger of reality, mapped to `refs/heads/chat/{id}`.
*   **Candidate:** Represents a "Fast" branch. It holds unverified tool outputs and file modifications generated by a sub-agent, mapped to `refs/heads/candidate/{id}`.
*   **Candidate Sandbox:** A physically isolated, short-lived working directory where agents can safely create, read, and modify files before they are merged into the main Thread.

## The Dual-Write Architecture

### 1. The Write Model (Git Source of Truth)
The Event Bus broadcasts all occurrences (prompts, tool calls, responses) to physical disk subscribers.
*   **`LedgerSubscriber`:** Writes linear, append-only JSONL files to `chats/{id}/ledger/logs/`.
*   **`DigestSubscriber`:** Writes standalone, human-readable Markdown files to `chats/{id}/ledger/digests/`.
This ensures that the complete cognitive history of an AI is inherently version-controlled by Git and survives total database failure.

### 2. The Read Model (BadgerDB Graph)
The `GraphSubscriber` instantly mirrors all events into a multi-tenant `BadgerDB` instance (typically at `~/.graphdb`).
*   Instead of parsing `.jsonl` files on every request, the backend executes O(1) prefix scans using a global `{SpaceID}:{ChatID}` routing taxonomy.
*   This enables instantaneous extraction of chronological timelines, sticky digests, and relational semantic `#tags` (Lenses).

### 3. Glass Box Rehydration
To protect against users manually altering Git history (e.g., `git reset --hard` or pulling from a remote), the `Rehydrator` engine runs a fast synchronization check every time a chat initializes. 
*   It compares the Git disk manifest `TotalEvents` against the BadgerDB sync state.
*   It can gracefully fast-forward missing events or execute a total O(N) rebuild if a hard history mismatch is detected.

## Core Components

### 1. ServiceManager (The Registry)
Handles all stateless, multi-tenant operations requested by the REST API, caching lazily instantiated `Service` instances locked to a specific `SpaceID`. It holds the global `GraphRepository` connection.

### 2. Service (The Session Orchestrator)
Dedicated entirely to the active lifecycle of a single ThinkSpace. It triggers the `Rehydrator` on boot, manages virtual sandboxes, physical file I/O, and fast-forwarding or dropping candidate branches upon human resolution.

### 3. ChatEngine (The Git Backend)
An interface that handles raw version control manipulation.
*   `GoGitEngine`: A pure Go implementation using `go-git` for in-memory operations and stashed ledger floating.
*   `GoExecEngine`: A wrapper around the native `git` CLI, utilizing native `git worktree` for performant candidate sandboxing.
